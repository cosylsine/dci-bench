# KaLM 三档池 v2：映射复杂度与 CPU/GPU 调度修复

v1 集群运行暴露了两个性能问题：Quora 导出对每个 query 都重新验证 522,363 条 ID 映射；单个 GPU worker 在排名结束后继续做三档 CPU/I/O 建池，直到整源完成才释放 GPU 调度名额。v2 修复这两处，仍使用原来 53 源、200/500/1000 三档、原始标签、短 ID、模型、指令和 seed。

## 改动

1. 导出先验证 query 和原始 qrels，再一次性批量 remap。完整映射的验证次数不随 query 数增长；保留等级、排序、原始 ID 反查和整 query 排除规则。
2. 导出、GPU 排名、CPU 建池成为独立阶段进程。CPU 进程隐藏 CUDA 设备。排名进程退出后，GPU context 随进程释放，父调度立即把空闲 GPU 分配给下一个已导出的来源，不等三档池结束。
3. 导出与建池有独立、有限并发的 CPU 队列，并与四个 GPU 排名 worker 重叠运行。已存在成功 ranking 的来源直接进入 CPU 验证/建池，不启动 GPU 编码。

默认导出并发 2、GPU 排名并发 4、CPU 建池并发 2、导出预取上限 8；CPU 阶段每进程最多 4 个数值计算线程。调度配置独立记录在计划和运行 preflight 中，不改变模型/池参数身份。确有资源余量时可通过 launcher 的 `--export-workers`、`--pool-workers`、`--export-prefetch` 调整；它们会增加 CPU、内存或共享盘压力。

这次不改变模型精度、文本截断长度或候选选择算法。建池依然需要 CPU 和共享盘 I/O；所有排名完成后的 CPU 收尾阶段可能出现 GPU 空闲。四卡利用率及全量峰值内存仍需要集群实测，不能由合成 smoke 推断。

## 从 v1 切换

先停止原来的 v1 集群任务，保留其全部输出目录，再在单节点 4×H100 任务中执行一次：

```bash
bash /mnt/afs/250010100/zxp/dci-bench/releases/data-pipeline/kalm_pool_batch_20261024_v2/launch.sh
```

不使用 `torchrun`。当前聊天环境无法直接控制集群作业；该命令由用户在旧任务退出后提交。旧进程加载的是冻结 v1 代码，编辑工作区不会修复已经运行的进程。

2026-10-24 19:57（北京时间）的封存后 preflight 显示 `/mnt/afs2` 仅余约 111 GiB，`df` 显示该共享盘使用率已接近 100%。这低于原先建议预留的 200 GiB；该建议是保守容量预算，并非全量实测需求。启动前应确认可用空间和文件配额足够，或先扩容；不要删除 v1 产物来腾空间。

v2 使用新的运行目录：

```text
/mnt/afs2/202609/embedding_models/dci-bench/eval_data/pipeline_pool_runs/kalm_pool_batch_20261024_v2
```

冻结计划引用 v1 的计划 SHA 和运行路径。启动后逐源固定可复用产物清单：

- 完成的 export 和 ranking：保留原绝对路径，校验身份、哈希及内容闭包后使用，不复制整个 corpus，不重新编码。
- 完成的池：校验后引用旧池路径。新 source 完成凭证中的 `pools[].path` 是结果路径的权威来源；部分池可能仍位于 v1 目录。
- 未完成 ranking 的完整 `.npz` 缓存分片：复制成新目录中的独立文件，校验大小和 SHA；后续编码继续验证缓存身份。临时分片不复用。
- 未完成 export/pool staging：保留在旧目录；新版本建立新 attempt，不把 staging 当作成功产物。

新版本不修改旧目录，也不允许新旧 run 路径相同或互相嵌套。v2 中断后仍执行同一条 v2 启动命令；阶段 receipt、源绑定、旧产物引用和缓存都会重新检查。不要删除 v1 目录，因为 v2 的完成产物可能引用其中的文件。

## 观察运行

各来源 `status.json` 记录阶段，`logs/` 保存阶段进程日志，`summary.json` 记录调度进展。根 `_COMPLETE.json` 只有全部 53 源、159 池完成时才生成。冻结包自身的 `_COMPLETE.json` 只表示计划和代码已封存。

验证记录位于 `eval_data/pipeline_validation/kalm_pool_batch_20261024_v2/`。Quora 同规模的合成 CPU 映射探针使用 522,363 个 ID、10,000 条 query，一次批量 remap 约 0.80 秒，完整映射只验证一次，标签与等级一致；这不是 Quora 完整导出计时，也没有生成半百万文档文件。

2026-10-24 验证结果：

- 113 项相关回归测试通过；补齐旧 v1 无独立 pools receipt 的场景后，8 项复用测试再次通过。
- 调度测试验证慢 CPU pool 与后续 GPU rank 重叠、四个 GPU slot 补位、CPU 隐藏 CUDA、失败不产生批次完成标记、完成 source 恢复仍走 CPU 全量校验。
- 实际 H100 MIG 上以 1001 合成文档、3 query 执行独立 export/rank/pools 进程，再以两个 CPU 进程验证恢复，总用时 126.51 秒；五个不同 PID 全部成功，只有一个 rank 进程可见 GPU。
- 生产冻结包的 59 个代码文件与实际 smoke 快照哈希完全一致；53 个来源条目和全部模型/池参数与 v1 完全一致。
- 未启动 v2 四卡全量任务；其运行目录尚未创建。v1 运行进程需要由用户在集群停止后再切换。
