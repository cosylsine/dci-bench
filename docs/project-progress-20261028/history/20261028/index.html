评测流程

下载规则图

一题从检索到评分

模型负责找出相关文档；Harness（运行控制程序）负责限定工具、计算用量、决定何时停止，并检查提交。

  1. 1

    开始：在指定文档中检索

    每题提供一个问题和 200 / 500 / 1000 篇候选文档。模型用搜索工具定位文档，用 read 打开正文，最后提交按相关性排序的 1–10 个文档 ID。

    标准相关性标签只在评分端保存，模型看不到。

    为什么限定范围

    让每次运行都有明确的候选集合，避免模型读到评分答案。

  2. 2

    每次调用都记账，一题共用一份预算

    总预算是整题累计用量的上限。每次模型调用结束，把实际输入和输出 token 加入账单；历史对话再次作为输入发送，也会再次计入。

    整题可以累计花多少
    96,000 / 128,000 / 192,000 token对应 200 / 500 / 1000 篇候选文档
    单次请求可以装多少
    65,536 token上下文上限；每次输出最多 1,024 token

    贯穿示例 · 500 篇候选文档

    第 1 次：8,000 输入 + 1,000 输出；第 2 次：12,000 输入 + 1,000 输出。

    累计用了 22,000，剩余 128,000 − 22,000 = 106,000 token。

    为什么按调用累加

    长对话反复传入模型也有成本。只看最终输出长度，会漏掉搜索过程中大量的输入开销。

  3. 3

    提前给提交结果和修正输出留出额度

    每次控制决策都重新估算：再检索一轮 → 提交一次结果 → 修正一次输出，合计还需要多少 token。这个估计随对话和工具返回内容增长而变化。

    算法先用最近一次实际输入、输出，再加新增消息，估计下一次输入；然后估算上述三次调用的总开销，与固定预留下限取较大值。

    接上例

    最近一次输入 12,000 + 输出 1,000 + 新增消息估计 1,000，得到下一次输入估计 14,000。

    当前公式算出预留 100,432。余额 106,000 高于预留，预算条件仍允许继续搜索。

    预留包含在原总预算内。它只估算一次修复，并不保证后面允许的三次修复都有额度。

    预算公式与当前参数

    设 N 为下一次输入的估计 token 数。最近一次实际输入和输出由模型服务返回；新增消息按 UTF-8 字节数换算，当前保守地按 1 byte = 1 token 估计。

    三次请求的预算估算
    预估请求计算上例 N = 14,000
    再检索一轮N + 1,024 + 4,09619,120
    提交结果N + 2 × 1,024 + 20,000 + 4,09640,144
    修正一次输出N + 3 × 1,024 + 20,000 + 4,09641,168

    每次请求预留 1,024 个输出 token 和 4,096 个安全余量；后两次还要重传预计最多 20,000 bytes 的新增工具结果，以及此前输出。因此历史输入会在三次请求中重复计算。

    预留 = max(固定下限, 3 × N + 58,432)

    三档固定下限为 24,000 / 32,000 / 48,000。当前参数下，动态估计始终高于这些下限；上例为 19,120 + 40,144 + 41,168 = 100,432。

    首次尚无实际用量时，系统提示和工具定义的字符串长度各除以 4、向上取整，再加新增消息的字节估计。后续以真实用量更新；估计用于提前决策，最终仍按实际用量扣预算。

    为什么提前预留

    如果搜索花光所有额度，模型就没机会整理和提交结果。历史越长，提交时重传上下文也越贵，因此预留不能只看固定值。

  4. 4

    余额接近预留时，停止自由搜索

    剩余额度 ≤ 预留，或同参数工具调用连续出现 3 次，都会触发干预。接下来先看模型有没有真正打开过正文：

    已经读过正文

    关闭搜索和读取工具，让模型用已有内容整理并提交文档 ID。这一步称为“收尾”。

    还没有读过正文

    最多给 2 轮，只允许 read 补读。读到后，余额高于预留就恢复搜索，否则收尾；仍未读到则失败。

    接上例：从余额判断走到提交

    假设模型已读过正文，继续检索后余额不再高于预留，就关闭工具、提交结果。此后即使文档 ID 写错，也只能用已有内容修正。

    即使预算充足，6 轮仍未读正文也会触发补读。模型也可以主动提交：列表结构正确且已读正文，就结束搜索、进入验收。

    为什么先看是否读过

    避免反复搜索却不看内容，也避免只凭文件名提交。要求的是整题至少读过一段非空正文，不要求每个返回 ID 都有对应读取记录。

  5. 5

    检查提交；可修复的错误再给机会

    提交必须是规定的 JSON：包含 1–10 个非空、不重复、在候选语料内的文档 ID，且整题已读过非空正文。失败时会把具体错误反馈给模型。

    还没进入收尾

    例如早期提交格式有误：可以继续搜索、读正文后重交；若正在补读，则仍只允许 read。

    已经进入收尾

    工具保持关闭，只能基于已有内容修正格式或文档 ID，不能重新搜索。

    两种修复合计最多 3 次，继续扣同一份预算。预算耗尽、超时等运行失败直接终止；不会为了修复追加额度。

    验收通过 → 用隐藏的相关性标签评分 → 保存排名、轨迹和成本。
    格式合格不等于检索正确。

    为什么区分两种修复

    给可纠正的输出错误重试机会，同时防止模型在停止搜索后，借修复重新开始检索。

验收细节与停止条件

“读过正文”指通过 read 取得至少一条非空正文读取记录；搜索输出、目录读取和空白正文不算。验收只检查整题是否有这样的记录，不把每个返回 ID 与读取记录逐一匹配。

标准输出为 {"ranked_doc_ids":["d1","d2"]}，也兼容单键 top_documents。非 JSON、空列表、重复 ID 或额外字段均不能触发主动收尾。结构正确但 ID 不存在时，可以先进入收尾，再无工具修复；错误反馈可包含文件名到正确 ID 的映射，不包含相关性答案。

  • 真实累计输入 + 输出达到总预算，记 token_limit；用量缺失记 usage_unavailable；单次输出超过 1,024 token 记 agent_error。
  • 发送前检查估计输入 + 1,024 + 4,096 不超过 65,536；控制或修复请求的估计成本（含新增指令）达到剩余额度时，不再发送，记 token_limit。
  • 每题最多 600 秒，包含启动、工具和模型等待；超时直接失败，不会提前触发收尾。最多 1,200 次模型响应；该轮尚未满足“列表结构正确 + 已读正文”才检查这个轮数上限。
  • 补读两轮仍无正文，且下一请求仍有预算时，记 tool_failure；预算不足会先记 token_limit。
  • 最多三次修复后仍无效，记 invalid_json。上述运行失败不进入修复；无效样本在主要平均指标中计零，同时单独报告有效样本的指标。
