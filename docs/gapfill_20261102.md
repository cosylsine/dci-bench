## 11月2日四卡任务中断诊断与恢复

原 attempt 为 `.gapfill_5090_4gpu_state/attempts/20261102T080257Z-50dd0303`。实际 smoke 通过（两条向量最大绝对差 `1.5683e-05`，cosine 最小值 `1.0`），四个 worker 分别完成14/14、14/14、13/13、13/13片，共54片。日志中的超长 token warning 来自截断计数；实际编码仍设置 max_length8192，四个 worker 均正常写出成功回执。

中断发生在控制进程的 CPU 合并阶段：canonical 从44片增至54片，只合入 worker-00 的44、48、…、80片，时间止于北京时间16:49:03；没有 `merge.json`、排名或候选池。原启动器未将 controller stderr/退出码保存到共享目录，因此现有证据不能确定是异常、内存终止还是调度终止，仍需平台主任务日志。10月31日旧日志中的 NVML allocator 错误属于另一轮运行，不用于解释本次中断。

只读核验确认剩余44个 worker 分片全部通过当前文本哈希、配置身份、向量 SHA-256、形状和有限值检查，第84片也正常。新增 `--merge-only --plan <原plan.json>` 支持仅在 CPU 恢复合并，保留原 attempt 和已有分片，另写恢复回执。新启动器同时保存 controller stdout/stderr、完整 traceback 与退出码；日志默认为 `results/gapfill-controller-logs/`，可用 `DCI_GAPFILL_LOG_DIR` 指定。`DRY_RUN=1` 和 `--check-only` 仍不创建日志或加载模型。

本次 CPU 恢复已成功：补入44片，保留原有54片，canonical **98/98片、99,930文档** 全部通过最终文本哈希、向量哈希和配置身份校验，退出码0；没有重新运行 GPU 推理。原失败 attempt、worker cache 和原有分片保留。恢复回执为新 attempt `20261102T132042Z-merge-37669d74/_MERGE_COMPLETE.json`。
