## Qwen3.8-27B：4 × RTX 5090 Smoke

当前20任务入口为 `scripts/launch_benchmark20_qwen38_5090.sh`，固定使用上述冻结 suite；每任务开发集中1题分别跑 Lite / Full，共40次。模型固定 `/mnt/afs2/202610/Qwen3.8-27B`，使用 `dci-vllm-qwen38` 服务环境与 `dci-bench` 评测环境。

```bash
cd /mnt/afs/250010100/zxp/dci-bench
CUDA_VISIBLE_DEVICES=0,1,2,3 DRY_RUN=0 bash scripts/launch_benchmark20_qwen38_5090.sh
```

默认不设置 `DRY_RUN=0` 时仅输出数据计划，不启动模型。需要先在目标节点单独验证CPU链路时，传 `--preflight-only`；它检查全部40项数据计划及真实Inspect/Pi/Bubblewrap链路，不调用GPU模型。完整启动同样先经过这些检查，缺少 `bubblewrap` / `ripgrep` 时调用既有系统工具安装脚本；安装或namespace检查失败会在模型加载前停止。

服务设置：TP=4、BF16、65,536上下文、`max_num_seqs=4`、显存利用率默认0.80（可用 `VLLM_GPU_MEMORY_UTILIZATION` 覆盖）、`max_num_batched_tokens=2048`、`--enforce-eager`；使用 `qwen3_coder` 工具解析器和 `qwen3` reasoning解析器。当前入口显式选择带GDN profiling预热修复的worker，详见下方记录。两档累计预算同为64,000 token。模型就绪后先做独立的合成工具调用预热，再执行40次benchmark Smoke；预热请求不计入40次。当前运行器按任务/档位顺序派发，每个Smoke batch仅1题，四卡共同服务一个模型，这轮不用于衡量4路query并发吞吐。

每次启动生成独立目录 `results/Qwen3.8-27B/benchmark-v2-smoke-runs/<时间戳>-<随机后缀>/`，启动时会打印路径。查看 `launcher.log`、`server.log`、`runtime.json`、`backend.json`、`warmup.json` 和 `smoke/summary.json`；结束后自动停止本次模型服务。`smoke/_COMPLETE`表示产物闭合，仍需检查summary中的completed/valid和逐题失败状态。通过这40次Smoke后，再做完整开发集预算与并发标定；不直接视为正式评测通过。

### 2026-11-05：CPU 沙箱预检失败修复

最近失败运行 `20261104T064614Z-uFD64o` 已通过40项数据预检，但4个 Inspect 进程均在启动 Pi 前报 `NoEventLoopError`。证据见该运行的 [process-0.log](../results/Qwen3.8-27B/benchmark-v2-smoke-runs/20261104T064614Z-uFD64o/sandbox-preflight/process-0.log)。运行目录未产生 `runtime.json`、`server.log`、`warmup.json` 或模型评测结果；这次失败发生在 CPU 阶段。

原因是非预取路径在 AnyIO 工作线程中读取 Inspect 的 `time.remaining`，其内部调用 `anyio.current_time()`，需要正在运行的异步事件循环。修复在工作区准备完成后通过 `anyio.from_thread.run_sync` 回到事件循环读取剩余时间；工作区准备耗时仍计入单题时限，耗时操作继续在线程内执行。未改变冻结查询、Lite/Full候选、64,000 token预算或模型参数。

新增真实 Inspect 时钟回归测试在修复前复现同一错误，修复后相关51项测试全部通过。独立真实 Inspect→Pi→Bubblewrap 预检通过4个进程及一个4样本并发批次，共8/8。完整启动入口随后以 `--preflight-only` 正常退出：40/40项数据预检与入口内8/8沙箱样本全部通过，外部模型调用为0，见 [launcher.log](../results/Qwen3.8-27B/benchmark-v2-smoke-runs/20261105T033118Z-dX30pP/launcher.log)。验证记录保存在 [20261105-benchmark20-smoke-fix-e2Z5nW](../results/implementation/20261105-benchmark20-smoke-fix-e2Z5nW/)。历史失败目录保留，4卡5090的GPU模型Smoke仍需使用上方命令在目标节点执行。

### 2026-11-05：后续 GPU 预热 OOM 检修

运行 `20261105T035335Z-OaAWmP` 已越过上述CPU问题：40项数据预检、8项沙箱预检、4卡5090 CUDA kernel检查全部通过，vLLM完成模型加载且 `/v1/models` 已就绪。随后第一个合成预热批次失败，benchmark尚未开始。[server.log](../results/Qwen3.8-27B/benchmark-v2-smoke-runs/20261105T035335Z-OaAWmP/server.log) 的第一处根因是 GDN `solve_tril` Triton autotune 抛出 CUDA OOM；[warmup.json](../results/Qwen3.8-27B/benchmark-v2-smoke-runs/20261105T035335Z-OaAWmP/warmup.json) 为0/24完成。失败时scheduler只派发了一个664-token请求，因此不能把原因归为4条长请求同时运行。

本地vLLM 0.17.0尚未包含已合并的 [上游修复 #36599](https://github.com/vllm-project/vllm/pull/36599)：profiling时GDN因 `attn_metadata=None` 直接返回，未调优的Triton内核直到KV cache分配后才第一次执行。本次日志每卡模型占12.79 GiB、KV预算15.2 GiB，首请求在这一阶段触发调优。日志没有给出失败的内部CUDA分配字节数。

当前启动器通过显式 `GDNWarmupWorker` 在每个服务进程内接入该profiling修复：KV分配前按实际TP/head/state dtype预热T=16/32/64，覆盖全部BT调优键；每层预热失败直接终止，全部GDN层成功才允许KV分配。代码在仓库内，未修改共享site-packages；版本限定为已审查的0.17.0，修复来源与源码哈希记入 `runtime.json`，并随其签入 `backend.json`。额外把显存利用率默认值由0.90降至0.80，为请求执行留出余量；64k上下文、BF16、TP4和64,000 token预算保持原值。

加载权重前新增 `gdn-kernel-preflight.json` 检查，在每张可见GPU运行原生Triton的16/32/64/664/2048-token小张量形状。探针与模型一致使用BF16输入、config指定的FP32 SSM状态，并在回执记录dtype；不能用默认BF16状态的通过代替这项验证。该独立进程只验证内核，服务worker仍在自己的profiling阶段重新预热，不能依赖另一个进程的内存调优缓存。
